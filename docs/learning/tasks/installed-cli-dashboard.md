# 설치된 CLI 대시보드와 탭 기능 점검

## 요청과 범위

2026-10-13: 실행 중이지 않은 CLI도 대시보드에 표시하고 각 탭 기능과
"찾았지만 삭제할 수 없음"의 원인을 점검한다. 대시보드 구현은 승인됐으며,
삭제 연동 확대는 이번 점검의 제안이다. 실제 CLI 삭제·업데이트·세션 재시작은
이 작업의 검증으로 실행하지 않는다. 사용자 직접 확인·이해는 미확인이다.

## 변경과 이유

- 기존 `Workspace`는 `snapshot.installations`만 표시했다. 운영 스냅샷에는
  엔진 등록 OmO 1개와 설치 카탈로그 11종이 있어 10종이 빠졌다.
- `web/dashboard.ts`의 `installedCatalog`, `catalogContainsInstallation`으로
  카탈로그를 우선 표시하고 경로가 일치하는 엔진 행을 중복 표시하지 않는다.
  선택이 필요한 복수 설치, 실행 중이지 않은 CLI, 미지원 CLI도 남긴다.
- `web/catalog-dashboard.tsx`는 기존 카드·탭·확인창을 재사용한다. 버전,
  최신 조회, herdr 세션, 자동화와 설치 위치를 한 행에서 확인한다.
  세션 수는 같은 CLI의 관찰값이지 선택 설치의 소유·삭제 가능 증명이 아니다.
- `catalog-check`는 기존 `updates.targetFor`와 `latestCatalogVersion`을 호출하되
  설치·정책을 변경하지 않는다. 설치 선택·경로·버전에 조회 결과를 묶어
  조회 도중 대상이 바뀌면 옛 결과를 표시하지 않는다.
- 최신 버전과 같음·새 버전 있음·설치가 더 높음·비교 불가·실패·미지원 상태를
  구분한다. 최신 여부는 세션 실행 버전과 별개다. 조회 결과는 서비스 메모리에
  있으며 서비스 재시작 후 재조회가 필요하다.
- 수동 업데이트는 기존 출처 검증과 계획 revision을 사용한다. 확인창에서
  승인해야 실행되며, 이 경로는 세션을 유지한다. 기존 업데이트 구현이 실행
  시점 최신 버전을 받으므로 조회 버전에 고정된 업데이트라고 표시하지 않는다.
- 자동 확인 성공 결과도 같은 표시 상태에 연결했다. 준비된 업데이트 작업은
  요약과 기록에 함께 표시한다.

## 탭별 검토

| 탭 | 확인한 역할과 결과 | 남은 개선 제안 |
|---|---|---|
| 대시보드 | 설치 전체·조회·세션·자동화 진입점으로 수정. 엔진 등록 여부 때문에 누락되던 CLI 복구 | 설치 지원 상태를 사전에 더 정확히 분류 |
| CLI 설치 | 전체 카탈로그, 설치 계획, 설치 위치 선택, 기본 실행 경로 전환, 제거와 보관 | 제거 가능성·제한 원인을 클릭 전 표시. 설치 탐지와 삭제 검증 구분 |
| 터미널 세션 | herdr 창과 업데이터에서 시작한 세션 표시. 외부 터미널 제외. 설치·실행·엔진 버전 구분 | OmO 전체 백그라운드 종료 신호가 없어 unknown 자동 재시작 제한 유지 |
| 업데이트 기록 | 엔진·카탈로그 업데이트 결과. 준비 상태도 누락하지 않도록 연결 | 설치·삭제·기본 경로 변경 이력은 현재 각각 다른 화면에 있어 통합 작업 기록 검토 |
| 자동 업데이트 | 설치별 저장 정책과 지원 제한. 설치 먼저, 세션 정책 별도 | 설치 종류 수준 `check-source`와 실제 대상 검증 성공을 분리해서 표시. 조회·준비 실패 복구 진입점 보강 |

문구상 문제: 세션 탭의 상단 설명은 같은 대화 재시작을 넓게 약속하지만
실제 지원은 개별 카드 조건으로 제한된다. 기록 화면의 빈 상태는 설치 화면에서
업데이트를 준비하라고 안내하지만 실제 수동 준비 진입점은 대시보드다.
자동화 탭과 대시보드 상세에 설치 선택·이력이 중복된다. 탭 재구성은 미실행이다.

## 삭제 제한: 실제 읽기 전용 진단

`discoverRemoval`을 실제 설치 경로에 대해 호출했고 제거 명령은 실행하지 않았다.
패키지 관리자 실행 경로는 진단 세션의 PATH를 사용했다.

| CLI | 결과 | 코드·실제 설치 근거 |
|---|---|---|
| Codex | npm 제거 대상 검증 성공 | nvm v24.20.0의 `@openai/codex` |
| Gajae Code, Oh My Pi, OmO | Bun 제거 대상 검증 성공 | 직접 전역 의존성과 `~/.bun/bin` 실행 경로 일치 |
| Antigravity, Claude Code, Grok, Kimi Code, 선택된 OpenCode | 현재 제거 연동 미지원 | 공식 독립 실행 파일 경로. npm/Bun 패키지 또는 앱 전용 설치 영수증이 아님 |
| Kilo | 출처는 앱 전용 설치로 일치하지만 검증 한도 초과 | 영수증 recipe hash·경로·심볼릭 링크 일치. 패키지 트리 836개 항목, 545,310,350바이트로 `fingerprint`의 512,000,000바이트 한도 초과 |
| Pi / Senpi | 독립 Bun 전역 설치로 검증 불가 | `.bun/install/global/node_modules/.bin/pi`로 발견. 전역 package.json 직접 dependencies에 Senpi 없음, `~/.bun/bin/pi` 없음 |

OpenCode에는 Homebrew 설치도 발견되지만 선택된 기본 경로는 별도 독립 실행 파일이다.
다른 설치의 관리자를 보고 현재 선택 설치도 제거 가능하다고 판단하면 안 된다.
Pi 하위 패키지 제거는 OmO에 영향을 줄 수 있어 독립 CLI 제거로 취급하면 안 된다.

원인은 `catalog-removal-target.ts`가 여러 검증 실패를 `null`로 합치고,
`catalog-removal.ts`가 이를 `manual_removal_required`로 바꾸기 때문이다.
`web/app.tsx`의 단일 설명은 Homebrew 지원 사실과 Kilo 검사 한도를 전달하지 못한다.
"발견 가능"은 실행 경로·버전만으로 판단하지만 "제거 가능"은 패키지 소유,
보존 범위, 영수증, 파일 변경 여부까지 검증해야 한다. 원리상 분리는 필요하지만
현재 지원 범위와 원인 표시는 부족하다.

권장 순서:

1. 검증 결과를 미지원 설치 방식 / 하위 패키지 / 영수증 불일치 / 검사 한도 /
   실행 중 / 설정 참조로 나누고 카드에 해당 원인과 다음 행동을 표시한다.
2. Kilo는 설치 영수증을 살리되 큰 파일을 스트리밍 검증하는 방식으로 개선한다.
   바이트 한도를 무조건 없애거나 실행 파일만 지우는 방식은 쓰지 않는다.
3. 공식 독립 설치별 제거 범위·현재 버전 링크·보존할 데이터·자동 재설치 여부를
   별도로 확인한 뒤 어댑터를 추가한다. npm 제거 명령을 대신 적용하지 않는다.
4. 하위 패키지 Pi는 "OmO가 사용하는 실행 도구"로 표시하고 독립 제거에서 제외한다.

## 확인 순서와 직접 검증

1. 대시보드의 설치 수를 CLI 설치 탭의 설치됨 필터와 비교한다.
2. 실행하지 않는 Codex의 최신 확인을 누른다. 조회 결과만 바뀌고 정책과 설치
   버전이 바뀌지 않아야 한다. 네트워크·출처 실패는 미지원/실패로 남는다.
3. OmO 세션 링크는 OmO의 herdr 창만, Codex 링크는 Codex만 표시해야 한다.
4. 새 버전이 있는 항목에서 업데이트 준비 후 취소한다. 설치가 바뀌면 안 된다.
5. 이상하면 카탈로그 선택·실행 경로 → 최신 조회 오류 → 관련 작업 revision →
   서비스 연결 상태 순으로 확인한다.

## 검증 기록

- 초기 변경: 관련 75개 테스트 통과, 타입 검사 통과.
- 실제 운영 스냅샷을 사용하는 격리 화면: 11종 표시, 14개 OmO herdr 세션 표시.
- `bun test web test/app`: 447 pass / 0 fail, 37개 파일, exit 0.
- 확인창 배치 보완 후 관련 화면 테스트 24개, `bun run typecheck`,
  `bun run build` 통과. 마지막 CSS 선택자 보완 후 빌드 exit 0.
- TypeScript LSP 오류 없음. CSS LSP는 로컬 Biome이 없어 실행하지 못했으며,
  번들 생성과 실제 computed style 및 화면으로 한 열 배치를 검증했다.
- 1440×1000과 390×844, 라이트·다크에서 카드와 확인창을 직접 확인했다.
  가로 넘침 없음. 모바일 메뉴 열기/탭 전환/닫힘, 목록 마지막 Pi 표시 확인.
- 조회 클릭은 `catalog-check`만 전송한다. 격리 준비 상태에서 확인창의 초기
  포커스는 제목이고 revision 변경 시 실행 버튼이 비활성화된다. 취소로
  업데이트 명령이 전송되지 않음을 확인했다. 실제 업데이트 실행은 미검증이다.
- 다섯 상위 탭을 실제 렌더링했고 Codex 상세 세션 0개, 자동화 토글의 저장된
  상태, 준비 작업 기록 연결을 확인했다. 모든 기존 기능의 전수 E2E는 아니다.

## 로컬 반영

- 같은 상태 저장소 `/Users/<user>/.local/share/cli-updater`, 같은 주소
  `http://127.0.0.1:62204`에서 웹 서비스만 정상 재시작했다.
  PID 43793 → 88272. CLI 프로세스 종료·설치 변경 명령은 실행하지 않았다.
- 실제 인증 화면에서 설치 11종을 확인했다. 서비스 ready,
  failure=null, observationFailure=null. 기존 herdr 세션 14개의 PID와 시작 시각
  모두 일치했다.
- 실제 Codex의 최신 확인 클릭 결과: 설치 0.162.1, 최신 0.162.1,
  status=current, failure=null. 새로운 업데이트 준비 작업 0개.
- 공개 패키지·사이트 게시가 아닌 로컬 서비스 반영이다. 삭제 지원 확대,
  탭 재구성, OmO 자동 재시작 계약 구현은 수행하지 않았다.
