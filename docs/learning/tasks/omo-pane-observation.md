# OmO pane 연결과 자동 재시작의 확인 범위

## 요청과 승인

2026-10-13: 설치 전부터 있던 pane과 이후 생성되는 pane을 모두 관리하고,
대화 연결 → 실제 상태 → 같은 대화 재시작 순서로 구현하도록 승인받았다.
운영 CLI 강제 종료나 엔진 전역 설치 변경은 수행하지 않았다.

## 코드에서 확인한 원리

- `omo thread list --all-scope --json`은 실행 TUI의 소켓과 대화 파일을 제공한다.
  `status: live`는 응답 가능이라는 뜻이지 작업 종료가 아니다.
- `observations.ts`는 현재 프로세스의 lsof UNIX 소켓과 목록을 정확히 연결한다.
  cwd나 최근 수정 파일을 골라 추측하지 않는다. 숨겨진 엔진 자식의 소켓은
  같은 wrapper까지 연결하되 별도 CLI의 소켓은 빌리지 않는다.
- `omo-threads.ts`는 endpoint의 generation 레코드를 읽는다. PID와 시작 시각,
  실제 소켓 소유가 맞을 때만 `runningEngineVersion`으로 표시한다.
  senpi 엔진 버전은 OmO 패키지 버전과 다르며 서로 대입하지 않는다.
- `get_state`는 모델 응답, bash 실행, 압축, 입력 큐, 입력 초안과 질문 상태를
  제공한다. 그러나 배포된 엔진은 `hasSessionWork`, `hasActiveWakeSource`를
  보내지 않는다. 마지막 JSONL의 assistant 메시지도 대기 상태의 증명이 아니다.

## 구현과 선택 이유

대화 연결과 엔진 버전은 기존 pane에도 즉시 사용할 수 있다. 상태는 작업 중,
응답/초안 대기, 전체 작업 종료 미확인을 구분한다. CPU가 낮고 입력 프롬프트가
보이더라도 백그라운드 도구가 남을 수 있어 이를 자동 종료 권한으로 쓰지 않는다.

`pane-restart.ts`는 OmO 종료 전에 대화와 프로세스 신원을 다시 관측하고,
불완전한 상태이면 `session_activity_unverified`로 입력하지 않는다. 재개 완료는
새 프로세스의 시작 시각, 동일 대화 ID, 엔진 버전 관측을 요구한다.

## 실행 근거와 미완료

- 실제 운영 OmO pane 14개 모두 대화 및 실행 엔진 버전을 읽기 전용 확인했다.
- 연결 테스트 첫 실행 59개 통과. 관련 app/web 전체 438개 통과 뒤 타입 오류
  3개를 수정했고, 수정 대상 회귀 테스트와 typecheck/build는 exit 0이었다.
- 실제 UI는 최신 제품 빌드와 실측 스냅샷을 사용하는 별도 읽기 전용 서버에서
  desktop 1440, phone 390, light/dark를 확인했다. 운영 서버 반영 증거는 아니다.
- 운영 세션을 종료/재시작하지 않았다. 격리 테스트의 성공은 배포판의 자동
  재시작 지원 증명이 아니다. 배포판 전체 자동 재시작은 미완료다.
- 최종 변경 대상 테스트 88개, typecheck와 build가 exit 0으로 끝났다.
- 엔진 측 종료 제어 구현 여부 질문은 30분 무응답으로 종료됐다. 해당 구현과
  그에 의존하는 실제 재시작 검증은 이번 실행에서 제외하고 미완료로 보존한다.
  운영 웹 서비스는 갱신하지 않았다. 화면은 직접 확인했지만 독립 시각 리뷰는
  수행하지 않았으므로 전체 UI 승인이나 운영 준비 완료로 기록하지 않는다.

## 남은 핵심 계약

### 운영 대시보드 반영 (2026-10-13 후속 승인)

사용자 "반영해줘" 승인으로 유휴 업데이터 서비스만 정상 종료 후 같은 주소
`http://127.0.0.1:62204`에 재시작했다(PID 525 → 43793).
실제 API는 ready, failure/observationFailure 없음. OmO pane 14개 모두 대화와
실행 엔진 버전이 연결됐고 재시작 전 14개 PID 및 시작 시각이 그대로 유지됐다.
실제 인증된 브라우저에서도 실행 엔진 표시, 대화 연결, 빈 native 패널 숨김을
확인했다. 엔진 변경과 CLI 세션 종료/재시작은 수행하지 않았다.

단순 busy 필드 추가만으로 완전한 자동 재시작이 되지는 않는다. 조회와 종료
사이에 새 입력이 들어올 수 있으므로 엔진 쪽에서 입력 접수 잠금과 모든 작업
종료 확인을 하나의 조건부 종료 요청으로 처리해야 한다. 기존 엔진을 바깥에서
관측하는 업데이터만으로 이 보장을 만들 수 없다. 현재 사용자 설치를 임의로
패치하지 않았다.

## 관련 보완

- 네이티브 대상과 기록이 모두 없으면 혼동을 주는 native 패널을 숨긴다.
- `installation-references.ts`는 알려진 설정/확장 디렉터리의 설치 경로 참조를
  통합 검토에 표시하고, 승인 직전에 다시 검사해 발견하면 제거하지 않는다.
  대화·자격 증명·로그는 검색하지 않는다. 임의의 모든 사용자 파일을 검사하는
  기능은 아니며 설정 자동 재작성도 수행하지 않는다.
- Claude는 SessionStart, Stop, SubagentStart/Stop 훅을 통한 신규 관측 경로가
  공식 제공된다. Stop 한 번만으로 전체 작업 종료를 주장할 수 없다.
- Codex는 app-server의 thread list/resume 및 공유 서버의 agents 명령을
  제공한다. 저장 대화 열거는 특정 기존 TUI 프로세스의 소유권 증명이 아니다.
  두 CLI의 신규 연결 구현 및 운영 검증은 이번 OmO 단계에서 수행하지 않았다.

## 직접 검증과 장애 확인 순서

세션 화면에서 대화 제목/ID, 실행 엔진 버전, 상태 미확인을 구분한다.
연결이 빠지면 thread list → 현재 PID의 UNIX 소켓 → 세션 헤더 순으로 확인한다.
엔진 버전이 빠지면 generation 레코드와 PID 시작 시각을 확인한다.
재시작 거절은 조회 실패와 작업 중, 전체 종료 미확인을 구분해 확인한다.
사용자 직접 검증과 이해 여부는 아직 확인하지 않았다.
