# 터미널 세션 식별과 버전 표시

## 문제와 변경

외부 세션의 디스크 패키지 버전은 실행 중인 프로세스의 버전을 증명하지 않는다. `web/app.tsx`는 실행 버전 미확인을 주요 정보로 표시하고 설치 버전을 실행 상세로 옮겼다. 카드 제목은 확인된 대화 제목, 실제 작업 폴더, 터미널 순으로 선택한다.

`src/app/observations.ts`는 ps의 PID·시작 시각·상태와 배치 lsof의 cwd를 사용한다. 좀비는 제외하고 PID 재사용은 시작 시각으로 구분한다. 한글 경로의 lsof UTF-8 이스케이프도 복원한다. 대화 연결은 정확한 session 인자, 열린 일반 JSONL 파일 또는 검증된 현재 대화 context만 허용한다. 최대 4096바이트의 첫 메타데이터 줄만 읽으며 대화 본문에서 제목을 추측하지 않는다.

`cli.ts`가 자신의 CLI 조상과 PI 세션 헤더를 확인해 PID·시작 시각·대화 ID·경로만 서비스에 전달한다. `main.ts`에서 구조를 검사하고 관측 때마다 다시 대조한다. 따라서 현재 대화 표시는 이 서비스를 연 대화의 확인된 연결이며 모든 터미널의 현재 선택 탭을 추적하는 기능은 아니다.

`controller.ts`는 성공 관측에서 사라진 프로세스를 한 번의 갱신 동안 종료 확인으로 표시한 뒤 제거한다. 조회 실패는 이전 항목을 현재 상태 미확인으로 바꾸며 마지막 성공 시각을 유지한다. 종료 확인 항목은 대시보드 실행 수에 포함하지 않는다.

## 재시작 후 현재 대화 재연결 (2026-10-12 추가)

`omo -r`처럼 CLI를 다시 열면 PID가 바뀌어 서비스 시작 때 저장한 context(PID+시작 시각)가 무효가 된다. 새 프로세스는 세션 JSONL을 열어 두지 않아(lsof에 cwd만 잡힘) 파일 기준 자동 재연결 근거가 없다. 따라서 `cli-updater open`(기본 명령)을 다시 실행할 때 `captureCurrentConversation()`을 다시 캡처해 `/internal/control` open 요청에 실어 보내고, `controller.bindCurrentConversation()`이 context를 교체한 뒤 즉시 재관측한다. 잘못된 shape은 zod strict 검증에서 거절돼 토큰을 발급하지 않는다. 자동 추적이 아니라 **명시적 재연결**이며, 서비스를 열었던 대화만 표시한다.

세션 카드 보조 줄에 설치 출처(관리 대상 설치 / 업데이터 검증용 설치 / 다른 설치)를 표시한다. 격리 경로(`isolated-omo`, `operating-native`, `single-session-*`)는 검증용이며 10월 6일 이후 기본 `omo`는 `~/.bun` 글로벌 설치를 쓴다.

검증: controller/server 회귀 43개 통과, 타입·빌드 exit 0. 실제 서비스 재시작 후 `open` 재실행으로 새 PID 63326(시작 19:03:44)이 같은 대화 ID에 연결된 화면을 캡처했다(`session-ui-rebind.png`).

- 관측·controller 관련 회귀 93개 통과. 추가 한글 경로 회귀 후 관측 테스트 54개 통과, controller 40개 이전 통과. 타입 검사와 제품 빌드 exit 0.
- 실제 프로세스 14개 모두 cwd 확인. 현재 대화 PID 66584, 시작 시각 `2026-10-06T06:41:38.000Z`, session `01a0fd29-2794-7e95-ab73-b7aecaa3750e`, cwd `/Users/<user>/Desktop/portfolio` 일치.
- 실제 localhost UI 1440×900/390×844, light/dark 네 화면 확인. 가로 넘침 없음(1440/1440, 390/390). 현재 배지 1개, 한글 경로 정상, 실행 상세의 설치 버전과 대화 ID 확인.
- UI 서비스만 재시작해 `http://127.0.0.1:62204`에 반영했다. 관리 세션·진행 업데이트가 없음을 확인했으며 CLI 세션은 종료하지 않았다.

## 한계와 직접 확인

실행 버전은 아래 '실행 버전 판정' 절의 시각 비교로 추론한다. 모든 외부 대화의 제목을 알 수 없으며 파일 연결이 없거나 여러 후보가 있으면 미확인으로 남긴다. lsof 접근 불가도 작업 폴더/대화 미확인으로 남긴다.

웹 새로고침 → 터미널 세션 → portfolio의 현재 대화 배지 → 실행 상세 순으로 확인한다. 관측 문제는 마지막 확인 시각/조회 실패 → PID와 시작 시각 → 작업 폴더 → 대화 파일 헤더 연결 순으로 확인한다. 이미 살아 있는 오래된 프로세스는 자동으로 종료하지 않는다.

## 실행 버전 판정 (2026-10-12 추가)

원리: 프로세스는 시작할 때 코드를 읽어 메모리에 올린다. 그래서 패키지 디렉터리(예: `omo-ai/`)와 `package.json`의 마지막 기록 시각(mtime) 이후에 시작한 프로세스는 디스크의 버전을 실행 중이다. 그 전에 시작한 프로세스는 시작 뒤 설치가 바뀐 것이므로 더 오래된 빌드를 실행 중이다.

- `observations.ts`의 `diskPackage`는 `installedAt`(디렉터리와 manifest mtime 중 큰 값)을 함께 반환한다. `runningVersionEvidence`는 세 가지다.
  - `started-after-install`: `runningVersion`을 디스크 버전으로 표시한다.
  - `started-before-install`: `runningVersion`은 null이고 카드에 "구버전 (설치된 X 이전)"과 재시작 안내를 표시한다.
  - `unknown`: 시작 시각이나 패키지 정보가 없다.
- 실제 결과: OmO 세션 11개 중 10월 12일 09:09에 5.1.30이 설치된 뒤 시작한 4개는 5.1.30이었다. 그 전에 시작한 7개는 구버전이었다. 구버전의 정확한 번호는 증명할 수 없어 표시하지 않는다.
- 한계: mtime 기반 추론이다. 같은 버전을 다시 설치하거나 파일을 touch해도 "바뀜"으로 본다(보수적). 패키지 정보가 없는 네이티브 실행 파일(ChatGPT 앱의 Codex, Claude 네이티브)은 미확인으로 남는다.
- 장애 시 확인 순서: 카드의 시작 시각 → `stat` 패키지 디렉터리 mtime → 실행 상세의 실행 파일 경로가 어느 설치를 가리키는지.
- 테스트: `test/app/observations.test.ts`에서 시작 시각 없음, 설치 후 시작, 설치가 시작 뒤 바뀜 세 경우를 확인한다.
