# 다중 설치 정리 (2026-10-12)

## 요구

같은 CLI가 Bun, npm, nvm 등에 여러 개 설치돼 있으면 터미널에서 어느 것이 실행되는지 헷갈리고 오래된 설치가 남는다. 관리 대상 하나만 남기고 나머지를 한 번에 정리하는 흐름을 만든다. 실제 제거는 설치마다 사용자 승인 후에만 한다.

## 구현

- `web/catalog-cleanup.tsx`의 `cleanupRows`가 설치마다 상태를 정한다.
  - 관리 대상: 유지한다.
  - 새 셸 기본 설정: 유지한다.
  - PATH 기본 실행: 먼저 기본 실행을 전환해야 한다.
  - 출처 미확인: 수동으로 확인해야 한다.
  - 실행 중 세션 있음: 세션이 종료된 뒤 제거할 수 있다.
  - 나머지: 제거 예정이다.
- 실행 중 판정은 같은 CLI의 세션만 센다. OmO에는 Pi 엔진 세션도 포함한다. 세션 실행 파일이 그 설치 루트 아래에 있을 때만 해당한다. 같은 npm prefix 아래에 다른 CLI 세션이 있어도 이 설치의 사용자로 보지 않는다.
- `CatalogCleanup`의 진행 순서는 다음과 같다.
  1. "관리 대상만 남기고 정리 (N개 제거 가능)" 버튼을 누르고 대화상자에서 목록을 확인한다.
  2. "N개 정리 시작"을 누르면 설치마다 기존 `remove-plan`을 호출한다. 서버가 제거 대상을 다시 판정한다.
  3. 사용자가 "이 설치 제거 승인"을 누르면 `remove-confirm`을 호출한다.
  4. 완료되면 다음 설치로 넘어간다. 실패하거나 결과가 확인되지 않으면 멈춘다.
- 새 서버 API는 없다. 기존 단건 제거 작업과 보호 검사(`guardRemoval`)를 그대로 쓴다. 보호 검사는 진행 중 작업, 자동 업데이트 대상 설치, 실행 중 프로세스를 막는다.
- 자동 업데이트가 켜져 있어도 정리할 수 있다(`installationControlsBlocked(entry, snapshot, { automation: false })`). 정리는 관리 대상을 건드리지 않는다. 자동 업데이트가 묶인 설치를 제거하려 하면 서버 guard가 `disable_automation_before_removal`로 막는다. "관리 대상 선택"과 "기본 실행 전환"은 기존처럼 자동 업데이트를 끈 뒤에만 할 수 있다.

## 선택 이유

일괄 삭제 API를 새로 만들지 않고 기존 단건 제거를 순서대로 실행한다. 설치마다 서버가 경로, 패키지 매니저, fingerprint를 다시 판정하고 사람이 승인한다. 그래서 목록을 본 뒤 상태가 바뀌어도 다른 것을 지우지 않는다.

## 실제 환경 사전 확인 (읽기 전용, 제거하지 않음)

| 설치 | 판정 |
|---|---|
| OmO nvm `5.0.0-0.beta.53` | npm 제거 대상 판정, 보호 검사 통과 |
| OmO npm-global `5.0.0-0.beta.48` | npm 제거 대상 판정, 보호 검사 통과 |
| Codex npm-global `0.153.2` | npm 제거 대상 판정, 보호 검사 통과 |
| opencode brew `1.1.48` | 대상 판정 실패(`manual_removal_required`) |

opencode는 정리 대상에는 보이지만 실행하면 실패로 표시된다. 실패하면 이후 항목 진행도 멈춘다.

## 한계

- 출처 미확인(`unknown`) 경로는 제거하지 않는다. 예: `~/.local/bin/omo`(Bun 단일 실행 파일, 5.1.21)는 2026-10-13 사용자 승인을 받아 직접 휴지통에 옮겼다.
- PATH 기본 판정은 서비스 프로세스의 PATH를 기준으로 한다. OmO 안에서 서비스를 띄우면 `~/.bun/install/global/node_modules/.bin`이 PATH 앞에 붙어 사용자 터미널과 결과가 다를 수 있다. OmO 런처는 두 경로를 같은 설치로 판정하므로(아래 '런처 판정 수정') OmO에는 이 차이가 없다.
- 제거 계획이 거절된 사유는 대화상자를 닫으면 화면 상단 안내에 보인다. `act`는 성공 여부만 반환한다.

## 함께 확인된 환경 문제

`~/.bun/install/global/node_modules/.bin/omo`가 2026-10-06 운영 검증 때 바꾼 `operating-native/prefix-r6`(5.1.19) 런처로 남아 있다. 원본은 `~/.local/share/herdr-cli-updater/launcher-backups/20261005-default-connection/node-modules-bin-omo`이며, 전역 `omo-ai/bin/omo.js`를 실행하는 omo-ai 런처 shim이다.

사용자 터미널은 `.zshrc`에서 `~/.bun/bin`을 앞에 두므로 영향을 받지 않는다. 하지만 OmO 하위 프로세스는 PATH 앞에 `node_modules/.bin`을 붙이므로, 그 안에서 `omo`를 실행하면 5.1.19 테스트 설치가 실행된다. 2026-10-13 사용자 승인 후 복구했다. 아래 '실제 정리 실행' 절을 본다.

## 직접 확인

1. 웹 UI → CLI 설치(또는 자동 업데이트) → OmO → 설치 위치 → "관리 대상만 남기고 정리".
2. 장애가 나면 다음 순서로 확인한다.
   - 버튼이 비활성: 인벤토리 상태와 진행 중 작업.
   - 항목이 실패: 상단 안내 문구(`manual_removal_required`, `running_sessions` 등).
   - 결과 미확인: 업데이트 기록과 제거 작업 상태를 확인한다. 같은 제거를 재시도하지 않는다.
3. 테스트: `bun test web/catalog-cleanup.test.tsx web/catalog-installations.test.tsx`.

## 검증

- app+web 회귀 421개가 통과했고 타입 검사와 빌드는 exit 0이다. `web/app.test.ts` 고정값에서 빠진 `installedAt`을 채운 뒤의 결과다.
- 실제 UI(`127.0.0.1:62204`): 자동 업데이트가 켜진 OmO에서 "관리 대상만 남기고 정리 (2개 제거 가능)" 버튼이 활성화됐다. 대화상자 목록은 관리 대상 유지, 제거 예정 2개, PATH 기본 1개, 출처 미확인 1개였다. 1440px 라이트와 390px 다크에서 가로 넘침이 없었다. "정리 시작"은 누르지 않았다.

## 실제 정리 실행 (2026-10-13, 사용자 승인)

- 대화상자 수정: 정리를 시작한 시점의 목록(`listed`)을 그대로 보여준다. 그래서 제거된 항목에도 "제거됨"이 표시된다. 마지막 중복을 지워 설치가 1개만 남아도 열린 대화상자는 닫히지 않는다(`rows.length<2&&!open`). 닫으면 결과를 초기화해 다음 정리를 새로 시작할 수 있다.
- 실제 UI에서 승인 버튼을 누르기 직전마다, 표시된 실행 파일 경로를 예상 목록과 대조했다.
  - OmO nvm `5.0.0-0.beta.53`과 npm-global `5.0.0-0.beta.48`: "정리 완료 · 제거 2/2".
  - Codex npm-global `0.153.2`: "정리 완료 · 제거 1/1". 설치가 1개만 남은 상태에서도 결과가 보였다.
  - 세 설치의 실행 파일과 패키지 폴더가 모두 사라졌다. 관리 대상인 OmO 5.1.30과 Codex 0.162.1은 남았다.
- `.bin/omo` 복구:
  - 기존 prefix-r6 런처는 `launcher-backups/20261013-before-restore/`에 보관했다.
  - 원본 백업으로 교체했다(같은 폴더에서 이름만 바꿔 한 번에 교체).
  - OmO 내부 PATH로 `omo --version`을 실행하면 `omo 5.1.30`이 나왔다.
  - 실행 직후 omo-ai가 표식을 인식해 런처를 최신 형식으로 다시 썼다. 결과는 `~/.bun/bin/omo`와 같다.
- `~/.local/bin/omo`(5.1.21): 쓰는 프로세스가 없음을 확인하고 `/usr/bin/trash`로 휴지통에 옮겼다. 이제 PATH에 있는 `omo`는 `~/.bun/bin/omo`와 `.bin/omo` 두 개이고, 둘 다 전역 5.1.30을 실행한다.
- 테스트 worker 17개(10/4 16개, 10/11 1개): 부모가 없고 임시 폴더에서 돌던 프로세스다. SIGTERM만으로 모두 종료됐고 하위 프로세스는 없었다. UI 서비스는 대상에서 제외했다.
- pin 갱신:
  - 서비스를 멈추고 `run/worker.catalog/auto-sources.json`을 `auto-sources.json.stale-20261013-010320`으로 보관한 뒤 재시작했다.
  - 새 pin 101개 중 지운 경로나 prefix-r6을 가리키는 것은 없다.
  - 업데이트 관리 대상은 OmO 5.1.30 하나다. 5.1.19 테스트 설치는 사라졌다.
  - pin을 다시 받으면서 최신 확인 기록이 비었다. 대시보드의 "최신 확인"으로 다시 채웠고, 결과는 최신 버전 5.1.30이다.

## 런처 판정 수정 (2026-10-13)

- 문제: pin을 갱신한 뒤에도 OmO 설치 목록에 `~/.bun/install/global/node_modules/.bin/omo`가 따로 남았다. "출처 미확인, 버전 미상, PATH 기본" 설치로 분류됐다.
  - Bun은 전역 패키지의 실행 링크를 `~/.bun/bin`과 전역 `node_modules/.bin` 두 곳에 만든다. omo-ai는 두 곳 모두에 같은 런처를 쓴다.
  - 그런데 앱의 판정 함수(`omo-installation.ts`의 `bunOmoEntry`)는 `~/.bun/bin/omo`만 인정했다.
  - 서비스 PATH 앞에 `.bin`이 붙으면(OmO 안에서 서비스를 띄운 경우) 정리 화면에 "먼저 기본 전환 필요"라는 잘못된 안내가 나왔다.
- 수정: `bunOmoEntry`가 정해진 두 경로를 모두 받는다.
  - 판정 조건은 그대로다. 실제 설치를 가리키는 링크이거나, 표식이 있고 쓰기 권한이 제한된 런처여야 한다.
  - worker의 별칭 규칙(`catalog-sources.ts`), omo-ai의 `BIN_ENTRIES`와 같은 범위다.
  - Bun 설치 제거는 여전히 `~/.bun/bin`의 실행 파일만 대상으로 한다. 제거할 수 있는 범위는 늘지 않았다.
- 테스트(`catalog-inventory.test.ts`):
  - 두 위치의 표식 런처가 Bun 설치 하나로 합쳐지고, 그 설치가 PATH 기본이 된다.
  - 같은 경로에 다른 곳을 실행하는 임의 스크립트를 두면, 별도의 미확인 설치로 남는다.
- 결과:
  - OmO 설치 목록은 Bun 5.1.30 하나(PATH 기본)다. Codex도 nvm 0.162.1 하나다. 그래서 두 CLI 모두 정리 버튼이 사라졌다.
  - app+web 회귀 422개가 통과했고 타입 검사와 빌드는 exit 0이다.

## 남은 것 (승인 범위 밖, 손대지 않음)

- `~/.local/share/herdr-cli-updater/operating-native/prefix-r6`(1.0G): 10/6 검증용 OmO 5.1.19 설치다. 이제 어떤 실행 경로도 이곳을 가리키지 않는다.
- `~/.config/herdr/updater-operations-*/`의 launch·profile 기록 파일 몇 개에 prefix-r6 경로가 남아 있다. 예전 플러그인 구조의 작업 기록이며, `omo` 실행 경로와는 관계없다.
- 휴지통에 있는 `omo`(120MB)와, 보관해 둔 pin 파일과 런처 백업은 필요 없으면 지워도 된다.
